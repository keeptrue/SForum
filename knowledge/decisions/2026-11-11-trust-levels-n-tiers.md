# 2026-11-11 信任等级：五档固定阶梯 → 运营自定义 N 档（1–8）

Status: **accepted**（2026-11-11，Lead 批准；实施中）
计划：`../plans/2026-11-11-trust-levels-n-tiers.md`（§1 验收口径与 §4 决定项为正本）
上游：`2026-11-10-trust-levels.md`（D1–D32，五档模型）、`2026-11-11-trust-levels-baseline-narrowing.md`（D34 基线门）。
本文件是**追加**决策，不改写上游条目；上游三份计划文件一个字未改（避免制造「已取代」的假历史）。

> 「被否方案」一节均为批准时的实际否决对象；批准时未列被否对象的条目照实写

## 问题

信任等级是一层「按累计行为自动升降的能力与限额层」，但它把档数写死在编译期：
`LevelCount = 5`、`nameSlugs [LevelCount]string`、`Policy.Levels [LevelCount]Requirements`、
`Policy.Limits [LevelCount]LevelLimits`（`apps/api/app/Models/TrustLevels/types.go:25,32,170,172`）。
运营想把「注册 7 天 / 30 天 / 一年」改成四档、六档或八档，只能改代码发版；
前端另有一份 5 元素本地数组与推荐默认值副本（`useTrustLevel.ts`、`useTrustLevelsForm.ts:37-40,98-103`），
两侧都要跟着改，且极易漂移。

要解决的是「让档数、档名、图标、阈值、限额、可解锁能力成为运营配置」，
**同时不改动「等级如何影响权限」的语义**。

## 两条成本洞见（本决策成立的基础）

1. **等级不落库，所以零数据库迁移。** 等级是每请求从 `user_activity` 六项 + `users.created_at`
   纯派生的值，`apps/api/database/migrations/` 与 `sqlc/` 对 `trust_level` 零命中。
   改档数只动一份 option JSON（`trust.levels`）的解码、校验与判定，不新增表/列，
   也不需要回填 job——「插档导致所有人等级变化」是派生值的自然结果，不是数据迁移问题。
2. **`Actor.TrustLevel` 保持 `int` 且语义仍是 rank，所以 Identity 与 Forum 零改动。**
   `apps/api/app/Models/Identity/types.go:220` 是 `TrustLevel int`。只要这个 `int`
   继续表示「第几档」，权限判定（`Actor.Can()`）、已挣得能力的装载期合并
   （`Identity/trust_level_grants.go`）、限额与基线门（`baseline_grants.go` 的
   `level >= int(LevelMember)`）全部不用动。真正的改动集中在 `TrustLevels` 领域包、
   后台 HTTP 面与前端编辑器。

## 决定 D-N1：身份与序号分离

**裁决**：每档有不可变 `id`（配置与契约身份）与 `rank`（1..N，判定与展示序号）；
`rank` 由 active 档位在数组中的顺序派生，不落字段。

**理由**：插序是需求的核心动作。用序号当身份时，「在第 2 位插一档」会把原第 2 档
已配的 requirements / limits / earnable 全部错挂到新档上。身份与序号分离后，
插序只改数组顺序，配置跟着 id 走（计划 §1 验收 2 就是这条的测试证据）。

**被否**：维持 `Level int` 同时充当身份与序号（现状态）。插一档就让整段已配阈值/限额/
earnable 错位到别的档上，运营必须事后重配，而**错位不报错**。

## 决定 D-N2：存储形状 v2

**裁决**：`{"schemaVersion":2,"tiers":[{id,name:{zh,en},icon,requirements,limits,earnable?,retired?}]}`。
数组顺序即顺序；`retired:true` 为软停用，保留全部配置，判定与 UI 跳过；TL0 不在数组内。

**理由**：单键 JSON 的既有形态（`trust.levels`，`config.go:14` 的 `ConfigSchemaVersion = 1`）
保持不变，只升版本与形状，迁移面最小。

**被否**：

- (a) 把 TL0 一起纳入 `tiers` 数组 —— 要把 `trust.new_user_*` 七键并进 `trust.levels`，
  等于一次改两块语义；而且基线门与账龄闸都锚在「rank 0」这个概念上，搬进数组反而多一层特例。
- (b) 档位与元数据分存两处（一张表或第二把 options 键）—— 多一处注册点就多一个静默丢弃口
  （options 的 5 道注册里漏第 5 道是历史上踩过的 T16），且一次保存要写两处，失败会半成功。

**wire 层细化（一）：公开与后台读面继续叫 `levels[]`，不随存储改名为 `tiers[]`。**
wire 是外部消费面，改名对存量消费方是破坏性变更；存储名与 wire 名不必同构，投影点只有一个
（后端 `payload.go`）。
**被否**：为了「命名一致」同时改存储与 wire —— 多出一批无收益 diff，且把一次内部模型改造
升级成对外破坏性变更。

## 决定 D-N3：命名池是编辑辅助，不是存储字段

**裁决**：存储只有 `name{zh,en}`；命名池只在 UI 里一键填入这两个字段。回退链：
`name[locale]` → `name[另一语言]` → 内置五档 i18n 键（id 命中时）→ `TL{rank}`。

**理由**：命名池是「让运营少打字」的编辑体验，不是数据模型。存 `name` 的两个语言字段
即可完整表达展示需求；回退链保证空值不会露出空标题。

**被否：存 `nameKey` + 优先级链。** 选它就要在服务端维护「key → 文案」的解析顺序
（哪一语言的 key 优先、池子升级后旧 key 还认不认、运营手填的值与池子值冲突时谁赢）。
这会长出**第二份真相**：`name` 字段与池子内容是两处可写的真值来源；同时把解析顺序
变成隐式契约，前后端各实现一遍就会分叉。文案是展示物，不是身份——身份由 `id` 承担。

## 决定 D-N4：图标白名单 + 默认序列

**裁决**：16 个 lucide 图标白名单，服务端校验；未选时按 rank 取默认序列
（前 5 = 现有 芽/叶/屋/山/冠）。零配置时视觉与今天一致。

**理由**：白名单让配置错误在保存时就暴露，而不是渲染成空白。

**被否**：图标允许自由输入 iconify 名。运营填错或填了不存在的集合，前端渲染成空白
且服务端无法校验，界面上看不出「这是配置错误」还是「这个图标就是这样」。

## 决定 D-N5：v1/v2 双向可读，只写 v2

**裁决**：`DecodeConfig` 同时接受 v1 与 v2；v1 在内存升级为 v2（id = 原 slug、name = 内置双语名、
icon = 默认序列）；`EncodeConfig` 只写 v2。`levelSlug` 字段**保留为字段名**，值 = tier id；
内置五档 id 不变 → 存量消费方不断。

**理由**：存量站点不必先跑迁移脚本；只写 v2 避免两代形状并存时的写回歧义。
`levelSlug` 是既有契约字段名（`apps/web/tests/admin/forum/trustLevels.test.ts:370-376`
就在断言它），改名字会打断所有消费方，而值换成 id 是语义等价（内置五档 id = 原 slug）。

**被否**：

- (a) 只支持 v2、不做 v1 兼容 —— 存量站点开机即读不到配置并回落到推荐默认，
  是一次**没有报错的数据丢失**。
- (b) 写一次性数据库迁移把 option 迁到 v2 —— 本来零迁移，凭空加一条不可逆迁移，
  且 options 值本来就在首次归一化时自愈。

**wire 层细化（二）：`level`（rank）与 `levelSlug`（tier id）在 wire 上并存。**
这是 D-N1 在传输层的投影：`level` 供 `TL{n}` 展示与判定比较，`levelSlug` 是稳定身份，
所有编辑动作以 `levelSlug` 为键。
**被否**：只发 rank —— 前端无法定位插序/停用目标，只能用易变的数组下标；只发 id ——
`TL{n}` 展示与 rank 比较全部要前端自己数位次。

**wire 层细化（三）：`TRUST_LEVEL_SLUGS` / `TRUST_LEVEL_MAX` 保留但收窄为「内置五档回退名 +
默认图标序列」，只允许出现在 `trustLevelName` / `trustLevelIconOf` 的回退分支。**
这条同时修正「消灭前端副本」的口径：**副本可以留，但只能留在回退分支里**，不能参与正常路径。
**被否**：直接删除以消灭第二份真相 —— 会连带删掉 5 个测试的类型保护，而那份类型保护是
唯一在编译期守着「内置五档 id 不变」的东西；收窄比删除的成本与回归面都更小。

## 决定 D-N6：id 生成 = `tier_<seq>`

**裁决**：`seq` = `max(所有档含 retired 的数字后缀, 5) + 1`，解码期派生，不存字段、
不接受客户端指定。

**理由**：服务端派生保证 id 唯一且不可被伪造；基线取 5 让内置 `newcomer..leader`
之外的 id 不与之碰撞；把 retired 也计入 max 是「永不复用」的实现方式——只软删除，
所以历史上出现过的 id 永远留在数组里，序号只会增大。

**被否**：

- (a) 客户端指定 id —— 可伪造、可在停用后复用。
- (b) 存 `nextTierSeq` 字段 —— 客户端可写、多一个会漂移的状态源。
- (c) 直接用 rank 当 id —— 插档即断，等于把 D-N1 否掉的东西从后门放回来。

## 决定 D-N7：active 档数 1..8

**裁决**：active 档数 1..8；至少保留 1 个 active。

**理由**：8 的上界来自前端可读性（D-N12 的 390px 实测）；1 的下界来自「阶梯至少要有
一档可判」，0 档会让判定无落点。

**被否**：

- (a) 不设上限 —— 40 档会让矩阵、判定循环和后台首屏一起失去可用性。
- (b) 只提供 3/5/7 预设 —— 运营无法精确表达想要的档数，等于半个需求。

## 决定 D-N8：减档 = 软停用 + 二次确认 + 常驻披露

**裁决**：停用保留全部配置、判定与 UI 跳过；保存前二次确认 + 常驻披露。
停用会撤回该档贡献的 `earnable`（可能降权），披露沿用现有 `UAlert` 常驻位，不用 Toast
（Toast 会 5 秒消失，把降权告知变成一次性弹窗）。

**被否**：

- (a) 二次确认后物理丢弃 —— 丢的是运营手配的 earnable 与限额，事后无处可查。
- (b) 禁止减档 —— 配错档数后只能整体「恢复推荐默认」重来。

## 决定 D-N9：推荐默认值唯一来源 = 后台读面 `recommendedConfig`

**裁决**：前端本地表降级为 `FALLBACK_TIERS`（仅读面不可用时兜底），并加一条等值测试防漂移。

**理由**：今天推荐默认值在前后端各有一份（`useTrustLevelsForm.ts:98-103` 与 Go
`DefaultPolicy()`），本仓库反复吃「第二份副本漂移」的亏。把真相收到读面，前端只留兜底
加一条等值测试钉住两者一致。

**被否**：继续保留前端推荐默认值副本作为真相。这份副本已经存在漂移风险，本次顺手收掉；
保留它等于承认「恢复默认」写出的值可能与站点推荐值不同。

## 决定 D-N10：四 tab，footer 是唯一保存入口

**裁决**：四 tab：`overview` / `tiers`（新）/ `thresholds` / `earnable`；默认仍 `overview`；
保存入口仍只有页级 footer 一处（单键全量覆盖）。

**理由**：与既有后台设置壳纪律一致（一处保存 = 一次一致写）。

**被否**：

- (a) 把档位管理塞进 `thresholds` tab —— 一个面板两个职责，且阈值 grid 在 8 档时已占满。
- (b) 档位管理拆成独立页 —— 需要第二套页头/工具栏 + 一条 V3 page identity，收益为零。
  论证结构同 `2026-11-11-trust-levels-standalone-admin-page.md`：只有「出现了第二个
  可编辑面」才够格升页，而这里恰恰是同一个 key 的同一个保存入口。

## 决定 D-N11：分档限额维持只读

**裁决**：本刀不做 `limits` 编辑器，保存时原样带回；新档 `limits` 写 `null`。

**理由**：控制单刀范围——档数/身份/命名/图标这一组改动已经同时动领域模型、配置形状、
契约与前端。`limits` 的 `RawMessage` 三分语义（省略→422 / null→继承 / 0→免冷却）
一旦进编辑器，需要新的空值与「全继承」UI 表达，属于独立的一刀。

**被否**：无被否记录（批准时未列被否对象）。注意「只读」不等于「可以丢」：省略 `limits`
会 422，所以保存时必须原样带回（`config.go:41-47` 的既有防线）。

## 决定 D-N12：矩阵 ≤6 档用表格，7–8 档按档分组卡片

**裁决**：`earnable` 矩阵 ≤6 档保持表格；7–8 档切成「按档分组卡片」
（每档一张卡、卡内 7 个勾选）。

**理由**：390px 下 8 列每列仅约 44px，勾选框与标签都无法容纳。

**被否**：8 列横向滚动。390px 下每列约 44px，勾选框点不中；首列 sticky 会把
「键 × 档」的二维语义撕成两段。

## 决定 D-N13：v1 → v2 的写入时机（recon 逼出的追加决定）

**裁决**：库值升级只在**运营保存**时发生（后台 PUT 与 options 归一化的写路径）；
启动、读路径、`DecodeConfig` 一律不得写库。

**理由**：归一化本来就是「写下规范形状」的机制；但让它隐式发生在读路径，会造出
「没人动过配置、库值却被改了」这种无法解释的现象——出问题时连是谁改的都查不出来。

**必须同时披露的代价**：旧版本二进制**无法解码 v2**，所以回滚不是「换回旧镜像就行」，
而是「换回旧镜像 + 同时回退 `trust.levels` 的值」。下次回滚的人不会想到这一条，
因此已同步写进热交接的 Next / Open Questions。

**被否**：

- (a) 让 `DecodeConfig` 也参与升级 —— 读路径写库，副作用藏在读里。
- (b) 让 `EncodeConfig` 继续写 v1 —— 等于永不升级，v2 字段全部丢失。

## 决定 D-N14：配置校验错误 = 统一机器码 + 结构化字段明细（`reasonCode` 为稳定枚举）

**裁决**：

- 机器码**恒为** `trust_levels.invalid_config`（前端与契约按它分流，**不按档位变码**）；
  明细放在 `data.details.errors[]`，**最多 8 条**。
- 明细四维：`rank`（TL1 起；`0` = 无法定位，例如全局字段、JSON 语法错、停用档位）、
  `tierId`（档位身份；新档与全局错误为 `""`）、`field`（固定取值域，含
  `requirements.<metric>` / `limits.<limitKey>` 这类子字段形态）、`reasonCode`（**稳定枚举**）
  + `params`（动态插值）+ `reason`（人读兜底，**不用于展示**）。

**理由**：`reason` 是 Go 侧中文散文。直接展示会让 en-US 站点看到中文报错，违反本仓
「后端不输出文案、i18n 由前端拼」的既有口径（`types.go` 顶上的包注释就是这条纪律，
`NameKey()` / `DescriptionKey()` / `ThresholdOptionKey()` 三个死生成器也正因它被删）。
**所以这条的真正裁决是：字段级明细不能用破坏 i18n 边界的方式换。**

**被否**：

- (a) 保持只有一句统一文案 —— 运营无法自救，计划 §8 明确要求「错误定位到具体档位与字段」。
- (b) 让控制器二次判断业务规则做校验 —— 那是第二份校验，两处迟早漂移。
- (c) 只给 `reason` 中文散文 —— 破坏 i18n 边界（见上）。

**实现状态（读代码可得，2026-11-11T18:2x）**：机器码已落地
（`Http/Controllers/TrustLevels/controller.go:20` 的 `CodeInvalidConfig`），明细上界已落地
（`Models/TrustLevels/config.go:50` 的 `MaxConfigErrorDetails = 8`），明细字段现值是
`Rank/TierID/Field/Reason`（`config.go:185-186`、`dto.go:68-74`）——**`reasonCode` 与
`params` 尚未落地**，`dto.go:73-74` 现注释仍是「Reason 直接展示给运营」，落地时要一并改。
### 附录 A：`reasonCode` 枚举的引用与判据（不抄内容）

枚举**已落地（29 条）**，但本附录不复制条目：枚举是契约，抄一份到这里就是第二份副本，
改了不同步就会有人照着过期列表写代码。只留三条引用与判据。

1. **契约位置**：`contracts/openapi/schemas/trust_levels.yaml` 的
   `TrustLevelConfigErrorDetail.reasonCode`（`required`，`enum` 29 条，**顺序即契约顺序**）。
2. **同源保证**：Go 侧 `trustlevels.ConfigErrorReasonCodes()` 与 OpenAPI enum 已做集合与顺序
   对拍（29/29 同序），并由 `TestConfigErrorReasonCodesAreStable`
   （`apps/api/app/Models/TrustLevels/config_test.go:410-443`）用**字面量**钉住——写成字面量而不是
   从常量表反推，是因为反推等于没断言。改一处必须同步另一处与前端 i18n 覆盖面测试。
3. **前端覆盖面护栏**：前端把 29 个 code 分成「表单可达的 14 条（逐条 i18n）」与
   「配置体损坏的 15 条（通用桶）」，断言**不重不漏**。所以后端新增第 30 个 code 会让前端测试
   红，而不是在 en-US 站点悄悄显示中文——**这是这套设计真正防住的东西**。
   现状：**前端侧尚未落地**（locale 里还没有 `reasonCode` 文案键、也无 29 条覆盖测试），
   故本轮按「契约要求」记录，落地前不得写成既有事实。

**另一处待修**：`TrustLevelConfigErrorDetail` 的**对象级**描述仍写着「把 `reason` 原样显示出来
即可自救」，与属性级 `reason` 的「不用于正式展示」自相矛盾——同一份契约里两种口径，
接入方读哪一段都可能。已报 backend 统一。

## 决定 D-N15：「恢复推荐默认」= 整份配置覆盖，不是「只重置阈值」

**背景**：页面原先把「恢复默认」实现成「本地用推荐阈值覆盖表单，限额与解锁不动」，文案也照
这个口径写（「恢复默认只重置各档的阈值。每档限额与能力解锁勾选保持不变」）。本刀把保存通道
切到专用端点后，恢复默认改成服务端的**整份覆盖**（`POST /admin/trust-levels/restore-defaults`
→ `EncodeConfig(DefaultPolicy())`）：档位数量与顺序、阈值、限额、新增解锁、名称、图标全部回到
推荐值，**已停用档会被移除**。

**裁决**：保留整份覆盖。

**理由**：推荐默认只有一处定义（服务端 `DefaultPolicy()`）；「只重置阈值」会留下「推荐阈值 +
手工限额 + 手工解锁」这种谁也说不清的混合态；一键恢复本来就该是完整回滚。

**代价与配套**：这是**破坏性动作**，所以恢复前必须有**阻塞式确认**，且确认框要**逐项列出会丢
什么**——五类：档位数量与顺序、阈值、限额、新增解锁、名称与图标。「整份配置」四个字不足以让人
做出知情决定。

**被否**：

- (a) 保留「只重置阈值」—— 需要第二个还原路径或第二份推荐值，两份迟早漂移。
- (b) 拆成两个按钮「重置阈值」+「重置全部」—— 增加一个运营必须理解的概念，收益不抵成本。

**连带影响（写文档时必须跟着改）**：UI 现值 `restoreHint`（zh/en 各一条）已随语义变更改写，
运营文档里引用的旧句「只重置各档阈值」**已失效**；本刀引入的新语义必须在模块注记里标明
「本刀引入」，不得写得像一直如此。

## 后果与遗留

- 生产代码 `rg -n "LevelCount" apps/` 必须零命中（计划 §1 验收 6）；
  `TRUST_LEVEL_SLUGS` / `TRUST_LEVEL_MAX` 只作为「无目录时的回退兜底」存在，
  且只允许出现在 `trustLevelName` / `trustLevelIconOf` 的回退分支（wire 层细化三）。
- **回滚是两步，不是一步**（D-N13）：旧二进制读不懂 v2 ⇒「回退镜像」之后**还要**把
  `trust.levels` 的值回退到 v1 形状，否则升级后的站点开机即读不到配置并回落到推荐默认。
- **本次一并修复的残留（不是历史遗留）**：三处「TL4 是最高档」的残留假设——
  `registry.go` 的 `All()` 实现成 `Grants(LevelLeader)`、`controller.go:108` 与
  `resolver.go:116` 用 `>= LevelLeader` 判顶——必须统一走 `Policy.LastRank()`。
  小研 recon 时这三处是实测现状；本次改造随刀修掉，**不得在模块注记里记成历史遗留**。
  **判据是编译期，不是正则**（常量声明已从 `types.go` 删除）：
  `rg -n "LevelLeader\s*(Level)?\s*=" apps/api/app/Models/TrustLevels/types.go` 零命中，
  且 `cd apps/api && go build ./...` exit 0（Go 里删掉的标识符被引用就编译不过），
  `rg -n "func .*LastRank" apps/api/app/Models/TrustLevels/` 命中 `types.go` 的 `LastRank`。
  **注释里保留这个字面量是预期的**（`registry.go:79`、`resolver.go:108` 记录的是这起事故），
  不构成残留；拿正则逼注释消失等于销毁事故史。
- 模块注记 `../modules/trust-levels.md` 的现状描述**必须等后端与前端落地后**再改写；
  提前写就是把计划当运行时事实。
