# 2026-10-26 v3.0.17 发版就绪清单（core + 商城）

## 0 结论：现在不能打 tag

三个硬阻塞，全部有证据：

1. **core HEAD 不含新动作**。`git grep -n 'extension.install.enable' HEAD -- apps/api` 为空，
   `git log --all -S 'extension.install.enable'` 也为空 —— 全仓没有任何提交包含它，
   只有工作区那棵树有（`apps/api/app/Support/ExtensionManifest/admin_micro_frontend.go:25`）。
   → 必须先 commit + push，pin 才有东西可指。
2. **商城 CI pin 指不认识新动作的提交**。`.github/workflows/ci.yml` 的 `ref: 10c2b21e8`，
   与 HEAD `8ab9f246b` 一样不认识 `extension.install.enable`；`validate-manifest` 会以
   `unknown admin host action`（`ErrInvalidManifest`）整份拒绝。
3. **商城取包链路不稳定**。同一 token 实测一次 200 但截断在 2.0 MB（应为 6.77 MB），
   一次 503 `upstream_unavailable`。发版说明里的「真机可用」现在还写不了。

## 1 落位判断（为什么写进 sessions，不新开 plan）

`plans/README.md` 的状态词只有 `draft` / `active` / `ready` / `blocked` / `blueprint`
（+ 归档三态），全部描述**任务书**。发版就绪清单是一次性操作序列，终点是 tag 与 release
记录，不是长期任务书；本仓既有先例是 `sessions/2026-10-23-release-v3.0.13.md`、
`sessions/2026-10-24-release-v3.0.15.md`、`sessions/2026-10-24-release-v3.0.16.md`。
故本文落 `sessions/`，不新开 plan，也不改现有 plan 的状态。

若之后要把「发版门禁」固化成长期流程，那才该写 `plans/…` 并标 `blueprint`，是另一件事。

## 3 版本身份

- 当前 `git describe --tags --long --dirty` = `v3.0.16-14-g8ab9f246b-dirty` → 下一个 tag `v3.0.17`。
- dev 的 `coreVersion` 由最近 tag 派生（现在是 `3.0.16+14.g8ab9f246b`，`+` 后是构建元数据，
  不参与 semver 比较）；打出 v3.0.17 后新 checkout 才报 3.0.17。

## 4 顺序（照做，别换序）

1. **core 提交**：把含 `extension.install.enable` 的整批（manifest 词表 + bridge + 弹窗 +
   i18n + OpenAPI + 测试）提交到 main。
   验收：`git grep -n 'extension.install.enable' HEAD -- apps/api` 非空。
2. **push origin/main**，等这次 push 的 `ci.yml` run 绿（G2 就是按这个 SHA 找它）。
3. **打并推 tag**：`git tag -a v3.0.17 -m "…"` → `git push origin v3.0.17`；
   release workflow 会自己再验 G1/G2。
4. **商城改两处，同一提交**：
   - `.github/workflows/ci.yml` 的 `ref:` 换成 **40 位完整 SHA**（不是 tag、不是短 SHA）。
   - `plugin/plugins/sforum.store/sforum.extension.json` 的 `sforumVersion` → `>=3.0.17`。
5. **store 门禁**：`bun run test`、`bun run typecheck`、`contract:generate` 无 diff、
   `capabilities:check`、plugin job 的 `build.sh` + `validate-manifest`。
6. **store 提交并推送**（推送前本地先跑一遍第 5 步，CI 只做复核）。
7. **发版记录**：写 `sessions/2026-10-2X-release-v3.0.17.md`，按 v3.0.16 的格式填
   G1–G6 实际结论、release run id、资产清单、GHCR 匿名拉取复核。

## 5 为什么 `sforumVersion` 要改（别写成为过 CI）

- **CI 不求值它**：`CheckSForumVersion` 全仓唯一生产调用点是
  `apps/api/app/Models/Extensions/lifecycle.go:720`（`ensureCoreCompatible`，
  安装/启用/激活/升级/回滚/重启路径）。store CI 的 `validate-manifest` 只做 schema +
  语义校验，不比对宿主版本。
- **要改的理由是语义诚实**：新包声明了 3.0.16 不认识的 `hostActions`。留在 `>=1.0.0` 时，
  3.0.16 宿主在解析清单阶段就报 `unknown admin host action`（`ErrInvalidManifest`），
  运维看到的是「清单非法」而不是「宿主太旧」。抬到 `>=3.0.17` 后，3.0.16 得到干净的
  `extension.core_incompatible`（安装 422 / 运行 409）。
- 代价：3.0.16 及更早宿主装不上这个插件 —— 这正是我们要表达的事实。

## 6 pin 的形态

- **40 位完整 SHA**。tag 可被移动、短 SHA 依赖仓库唯一性；发版记录要能反查到确切制品。
- 理想状态：`pin SHA == v3.0.17 指向的提交`，让「发布身份」与「CI 编译基线」是同一个提交。
- 如果 tag 之后 core 又合了新提交再改 pin，允许，但要在 store 提交信息里写明它基于哪个 tag。

## 7 回滚点

| 故障 | 回滚动作 | 副作用 |
| --- | --- | --- |
| tag 打错 / release workflow 失败 | `git push --delete origin v3.0.17` + 本地 `git tag -d v3.0.17` | 已产生的候选镜像与 draft release 要一并清理 |
| core 提交有问题 | `git revert <sha>` 再 push | 已拉过 v3.0.17 的实例不会自动回退（降发行线被 `ErrCoreUpgradeIncompatible` 拦） |
| store 的 pin 指错 | `ref` 改回 `10c2b21e8` 并推 | 该 pin 不认识新动作 → store CI 立刻红，等于把发版回退成不可发布状态 |
| `sforumVersion` 抬早了 | 改回 `>=1.0.0` | 3.0.16 宿主重新落到「清单非法」而非「版本不兼容」 |

## 8 发版说明里不能写的话

- 不能写「商城安装已真机验证」：真实公网包只做到路由/服务层 staged，
  已启用 / 已升级 / 已用 N 秒 / 影响面四条真机证据未取
  （见 `2026-10-26-install-evidence-acceptance.md` §1、§6）。
- 不能写「运行阶段平台不兼容已真机验证」：只有 Go 单测。
- 可以写：清单词表 + 宿主弹窗 + 桥接 + 平台预判（单测/服务层）+ 死锁三因移除（真机 DOM 证据）。

## 10 两个开放问题（建议，不拍板）

### Q1 主题装完仍要手动激活：要不要「安装并设为默认」？

背景：`outcome: 'staged'` + `stagedReason: 'theme'` 是当前唯一诚实的答案
（`decisions/2026-10-24-admin-page-host-action.md` 的 Honest limits：Host 不替操作员做激活决定）。

**选项 A**：新增第三个动作 `extension.install.activate-theme`，在宿主弹窗内完成
「安装 → 确认 → 设为默认」。
- 利：主题安装真正一键；与 `.enable` 对称；主题页仍是唯一权威（只是提前调用）。
- 弊：动作词表再扩一个 id → 老宿主整份拒绝（`unknown admin host action`），
  发布方必须再抬一次 `sforumVersion`；切换主题有全站可见后果，塞进「安装」语义里
  容易让人以为只是装包；「Host 不做激活决定」的边界要重写。

**选项 B（推荐）**：保持 `staged`，把结果面板的「去主题页完成激活」改成带
`?activate=<id>&version=<v>` 的深链，主题页高亮该主题并预选，操作员只点一次「启用」。
- 利：不动动作词表、不抬版本门槛、不改「Host 不做激活决定」的边界；两页操作压成
  「一次跳转 + 一次点击」。
- 弊：不是真一键；需要主题页支持查询参数预选（前端小改动）。

**推荐 B**。重开条件：真实用户反馈「装完主题经常忘了激活」，再升级到 A。

### Q2 非 super_admin 装可执行后端包、启用回落超管：要不要收紧成直接拒绝安装？

背景：现在非超管可以装（staged 成功），启用时回落 `staged / super_admin`，包留在本地等人启用。

**选项 A（推荐）**：保持现状，把确认框与结果面板的下一步写死（已有
`enableNoticeBodyDelegated`、`stagedSuperAdminTitle/Body`）。
- 利：安装与信任是两件事 —— 安装只落一个惰性包（不执行、不迁移、不启动）；
  拒绝安装会切断「帮超管把包准备好」这种正常协作；服务层授权没被削弱
  （`super_admin` 仍在启用时生效）。
- 弊：磁盘上会留下没人启用的包；非超管可能误以为「装好了就能用」。

**选项 B**：直接拒绝安装（`begin()` 的权限预检里加一条：包声明可执行后端且非超管 →
`install_permission_denied`）。
- 利：语义最干净，不留半成品。
- 弊：**安装前无法可靠判断「带可执行后端」**。这个判断现在来自安装结果
  （`requiresTrust`），预检阶段只有调用方传的 `expectedType`（plugin/theme），
  没有「是否带后端」。要真做，得让商店多传 `expectedExecutable: boolean` 并纳入身份绑定
  校验 —— 契约变更 + 老宿主兼容问题。

**推荐 A（保持）**。重开条件：出现「非超管装了可执行包 → 管理员误以为已启用」的真实误操作。
