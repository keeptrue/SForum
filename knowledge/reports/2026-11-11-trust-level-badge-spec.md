# 前台信任等级徽章：视觉规格

日期：2026-11-11
状态：规格定稿（实现由前端执行，本文不含代码）；**当前的展示位置口径变了**——产品要求信任等级标识只在个人中心（资料页）出现，论坛读面（话题列表/详情/回复）一律不显示，因此论坛徽章实现已 revert（`46c2f52cb`）。本文的形态/密度/对比度结论与展示位置无关，保留作将来在受限面加等级标识时的依据。
输入：`apps/web/app/assets/css/sforum-trust-colors.css`（9 色 token）、`apps/web/app/components/profile/SFTrustLevelCard.vue`（`--tl-accent` 阶梯）、`knowledge/reports/2026-11-11-trust-tier-color-palette.md`（对比度底表）

## 0. 一句话结论

采用 **「色点 + 档位数字」内联徽章**（无底色、无描边、不可点），两档尺寸：紧凑档 11px（列表/回复）、舒展档 12px（详情作者栏）。数字永远可读、颜色只做加速识别。全量实测最差对比度 **5.16:1（浅色）**、**5.53:1（深色）**，均高于 4.5:1。

## 1. 两个候选与选择

### 方案 A「淡底数字牌」
12% 档位色底 + 1px 26% 混色描边 + 档位色文字 `TL6`，圆角 4px，内边距 1px 6px。

- 优点：颜色面积大，档位一眼能扫；与后台档位行徽章同语言。
- 否决理由（实测）：牌内文字压在 12% 混色底上，在运营日间预设 `parchment`（卡面 `#fcf8ef`）下 **teal 只有 4.38:1**，低于 4.5:1。而 390px 列表恰恰是最需要保证可读性的场景。要救它只能给徽章再垫一层纯白底，等于在浅色卡面上开洞，视觉更脏。
- 次要理由：作者行已可能有角色徽章（底色/实心），再加一个带底的彩色牌，一行出现两个色块，颜色语义互相稀释。

### 方案 B「色点 + 档位数字」（采用）
6px 实心圆点（100% 档位色）+ `TL6` 文字（同色、tabular 数字）+ 无底色、无描边、透明背景。

- 文字压在**卡面本身**而不是混色底上，对比度按卡面核验即可：浅色最差 5.16（teal / parchment），深色最差 5.53（indigo / 公开页）。比方案 A 高 0.78。
- 数字承载信息、圆点承载色相：红绿色盲用户不依赖颜色也能读出档位，颜色只是加速识别。这是 9 档体系里唯一可靠的兜底。
- 水平占用 ~28–30px（`TL8` 最宽），是方案 A 的 2/3，给 390px 下的作者名留出更多截断余量。
- 与主题 accent 同色的问题（见第 2 节）在极小面积、纯文字形态下最不敏感。

## 2. 密度与尺寸

两档尺寸，不是三档：列表与回复的差异只有 1px 字号和 4px 间距，单独造第三档不值得，实现上应合并。

| 位置 | 圆点 | 点与数字间距 | 字号/字重 | 行高 | 与作者名间距 | 总宽（`TL8`） |
|---|---|---|---|---|---|---|
| 帖子列表（390px 作者行） | 6px | 4px | 11px / 600 | 14px | 6px | ~30px |
| 回复（缩进列表内） | 6px | 4px | 11px / 600 | 14px | 6px | ~30px |
| 详情页作者栏 | 7px | 5px | 12px / 600 | 16px | 8px | ~34px |

统一规则：

- 数字用 `font-variant-numeric: tabular-nums`，`letter-spacing: 0.02em`，`white-space: nowrap`，`flex: 0 0 auto`，避免作者名截断时把 `TL6` 挤成两行。
- 垂直对齐用 `align-items: baseline`（数字随名字基线），圆点用 `align-self: center` 微调 0–1px。不要用 line-height 撑高整行。
- 徽章整体 `user-select: none`：选中并复制作者名时不应把 `TL6` 带进剪贴板。
- 圆点 `aria-hidden="true"`；徽章本体给 `aria-label="信任等级 6"`（不需要读成 "T L 六"）。
- 390px 下若作者名 + 徽章 + 角色徽章总宽超出，**先截断作者名，不移除徽章、不缩小字号**。

## 3. 颜色用法

| 元素 | 用色 | 强度 |
|---|---|---|
| 圆点 | `--sf-tl-<slug>` | 100%（非文本元素，实测 ≥5.16，远超 3:1） |
| 数字 | `--sf-tl-<slug>` | 100% |
| 底色 | 无 | — |
| 描边 | 无 | — |

颜色只出现在两个不到 30px 的元素上，且同一档位两处同色同强度——这是"标记"而不是"控件"的关键：不加底色、不加描边、不加悬停遮罩，它就不会被误读成按钮或可点状态。

**与主题 accent 同色的避让（沿用"改形态不改色相"）**：

- violet 主题下 `--sf-tl-violet` 与该主题 `--sf-accent` 完全同色；amber 主题深色下 `--sf-tl-amber` 与 `--sf-accent-dark` 完全同色；rose 主题与 `--sf-tl-rose` 色相差 12°/22°。都不改色值。
- 靠形态区分：主题 accent 只出现在**按钮、链接、选中态**（有底色或下划线、有指针手型、可聚焦），徽章是**纯文字 + 圆点、无指针手型、不可聚焦**。两者视觉语法不同，即使同色也不会混淆。
- 一行内只允许一个颜色元素：如果作者行已经有实心/带底色的角色徽章（管理员、版主），TL 徽章降级为**纯数字、不带圆点**，用 `--sf-tl-<slug>` 上色。若两个都保留，颜色语义会被稀释，且 390px 会挤爆。

## 4. TL0（新成员）

**显示**，但不靠降透明度降权——透明度会让文字掉到 4.5:1 以下，这是硬约束。

- 形态区分：圆点改为 **1px 空心环**（盒子仍为 6px，用内描边绘制，填充透明，具体见 9.3 的防抖动要求），环线用 100% `--sf-tl-slate`；数字 `TL0` 用 100% `--sf-tl-slate`，字号字重与其它档一致。
- 实测：空心环描边与 `TL0` 文字在浅色最差 5.16（parchment）、深色最差 6.43（公开页底 `#1b201f`），均达标。
- "空心 vs 实心"是形状差异，在灰度、色盲、`forced-colors` 下都成立；同时天然复用了后台档位卡里 `[data-level="0"]` 的虚线语言，前后台一致。
- 判断依据：如果隐藏 TL0，那么"没有徽章"会同时表示"新成员"和"数据缺失"两件事，运营和用户都没法区分。所以显示，用最低权重显示。
- 若后续统计显示绝大多数发帖都是 TL0，作者行会变成一片 `TL0`，那时再讨论"只在详情页显示 TL0"。这是数据问题，不是设计问题，现在不做。

## 5. 未知档 / 旧数据 / 越界

降级顺序（从可信到不可信），任何一步都不要猜色：

1. `authorTrustLevel` 字段缺失，或 `level` 不存在 → **不渲染徽章**，也不留占位空白。列表与详情要保持同一判定，避免同一作者两处不一致。
2. `level` 存在但 `levelSlug` 不在 9 色白名单（旧数据、运营删过档位）→ 退化为**纯文字 `TL{n}`**，颜色 `--sf-fg-tertiary`，无圆点、无档位色。含义："这是历史档位，当前目录里已没有它"。
3. `levelSlug` 在白名单但 `color` 字段为空/不认识 → 按 `level` 索引在 9 色序号表里取 token（0=slate … 8=amber）。这是唯一允许的"按位次兜底色"，因为档位序号本身是语义。
4. `level` 超出 0–8（服务端配置被改动、MaxTiers 变化、脏数据）→ 按第 1 条隐藏。不要显示 `TL12` 这种越界数字，也不要用取模循环回 slate——那正是 9 色方案要消灭的病。
5. `color` 字段来自服务端字符串：前端必须走**冻结的白名单字典**映射到 `--sf-tl-*`，不得拼接进 `style` 属性。未命中即按第 3 条兜底。

隐藏徽章时不要留空容器、不要留 gap，否则作者名右侧会出现看不见的缩进。

## 6. 对比度实测

算法与 `knowledge/reports/2026-11-11-trust-tier-color-palette.md` 第 2.1 节完全一致（WCAG 2.1 相对亮度 + `(L1+0.05)/(L2+0.05)`）。预览面取实际会出现的 5 种卡面：日间预设 `pure_white #ffffff` / `paper #fffdf8` / `parchment #fcf8ef`，夜间 `#18181b`（详情/后台）与 `#1b201f`（公开页 `--sf-public-surface`）。

### 6.1 采用方案（方案 B）的最小值

| 档位 | 浅色最差（parchment `#fcf8ef`） | 深色最差（`#1b201f`） |
|---|---|---|
| slate (TL0) | 7.15 | 6.43 |
| teal | **5.16** | 8.86 |
| emerald | 6.73 | 9.47 |
| sky | 5.60 | 7.70 |
| indigo | 7.46 | **5.53** |
| violet | 5.38 | 6.06 |
| fuchsia | 5.97 | 6.70 |
| rose | 5.70 | 6.23 |
| amber | 6.69 | 9.88 |

**全量最差：浅色 5.16（teal / parchment）、深色 5.53（indigo / 公开页）**，文字与圆点两用均达标（4.5:1 文字、3:1 非文本）。

### 6.2 5 套站点主题下的差异

- accent 主题（teal / ocean_blue / violet / rose / amber）只改 `--sf-accent*`，不改 `--sf-tl-*`，也不改卡面，因此 **5 套主题下徽章数值完全相同**（上表即结论，不存在某个主题更差的情况）。
- 真正会改变卡面的是运营日间预设。`mist_gray` / `porcelain` 的卡面仍是 `#ffffff`，与 `pure_white` 同值；`paper #fffdf8` 比纯白低约 0.1–0.12；`parchment #fcf8ef` 最低，即上表取值。夜间两档都在表内。
- 结论：最差工况已被覆盖，不需要为任何主题单独准备色值。

### 6.3 被否决的候选（留档）

方案 A 的淡底牌在 `parchment` 上逐档实测：teal **4.38**（唯一不达标）、violet **4.51**、sky **4.71**、rose 4.68、fuchsia 4.92，其余 5.57–6.15。混合底的明度抬升把浅色档位整体往下压，teal 直接出线，violet 只剩 0.01 余量。这是方案 A 被否的直接实测依据，不是审美偏好；也说明"淡底 + 彩字"这条路在运营可换卡面的前提下先天不稳。

## 7. 交互边界（前台只读）

- **只读展示**：不响应点击，不进入键盘 Tab 顺序，无 `role="button"`，无指针手型，无悬停态变化（不加深、不放大、不显示阴影）。
- **不可点开**：不做「点开看档位说明 / 进度 / 权益」的入口。需要解释档位时，去个人主页的信任等级卡（`SFTrustLevelCard`），帖子内不给第二入口。
- **不携带任何计数**：不显示积分、不显示"还需 N 分升档"、不显示进度条、不显示下一档提示、不显示人数。帖子流里出现数字型指标会诱发比较与刷量动机，产品口径已排除。
- **不作为唯一信息源**：任何含义都不能只靠悬停 tooltip 承载；键盘与触屏用户拿不到 tooltip。
- **不参与布局回流**：徽章出现与消失不得导致作者名换行或整行高度变化；容器高度由名字行决定。
- **一致性**：同一作者在列表、详情、回复三处的档位必须一致；若载荷缺失，三处一起不显示（不要在列表显示、详情隐藏）。
- 屏幕阅读器读作「信任等级 6」，圆点不朗读；不要读成 "TL6" 字母。

## 8. 待确认（已裁决，见第 9 节）

- 作者行里 TL 徽章与角色徽章（管理员/版主）的**先后顺序**：本文按「名字 → TL 徽章 → 角色徽章」写，如果现有作者行是「名字 → 角色徽章」，则 TL 徽章排在角色徽章之后，且按第 3 节降级为纯数字。这一点取决于角色徽章的实际形态，需要前端确认后再定，不要两边各写一套。
- TL0 是否在列表页也显示（本文结论：显示）。若产品希望列表更干净，唯一允许的调整是"列表隐藏 TL0、详情与回复显示"，且三处判定要显式写明，不能靠默认值差异实现。

## 9. 排序与 TL0（lead 2026-11-11 裁决落地）

### 9.1 插入位置

作者名旁不存在角色徽章（管理员/版主标记）。实际存在的后缀节点只有两个：`sf-comment__op-badge`（「楼主」标，`topicDetail.opBadge`）与 `SFBadgeChip`（`topBadge`，最高级奖励徽章）。因此 TL 徽章是**插入，不是重排**：

| 位置 | 最终顺序 |
|---|---|
| 详情作者块（`SFTopicAuthorBlock.vue`） | 昵称 → **TL** → 奖励 chip（该处无楼主标） |
| 评论 / 回复（`SFCommentAuthorRow.vue` 的 `#name-suffix`） | 昵称 → 楼主标 → **TL** → 奖励 chip |

落点：评论行放进 `#name-suffix` 插槽，位于 `sf-comment__op-badge` 之后、`<SFBadgeChip>` 之前；详情作者块放在 `<SFBadgeChip>` 之前。两处都只新增一个节点。

### 9.2 为什么不动楼主标

- 楼主标表达的是「相对这一篇的位置」，属于内容上下文，紧贴昵称最合理；把它往后挪会削弱它与标题/楼层的关联。
- 它是现有 DOM 契约的一部分，挪动会影响已有的 `#name-suffix` 消费方和间距假设。插在它之后，既有节点位置和顺序全部不变，回归面最小。
- 三者的语义层次正好是「内容上下文（楼主）→ 身份属性（TL）→ 内容装饰（奖励）」；TL 在中间是唯一不需要解释的排法。
- 后缀内间距沿用容器现有的行内 gap，不为 TL 单独加外边距；TL 与左侧紧邻元素的视觉间距按第 2 节（列表/回复 6px、详情 8px）取，二者冲突时以容器 gap 为准，不叠加。

### 9.3 TL0 在列表也显示

列表不隐藏 TL0，与详情、回复一致。依据是第 7 节的一致性约束：列表藏、详情显示会制造「这页没徽章、点进去有」的疑问，而空心环在 11px 字号旁已经足够轻。

实现要求（避免布局抖动）：TL0 的空心环**盒子尺寸与其它档完全相同（6px）**，用 `box-shadow: inset 0 0 0 1px` 画 1px 环，不要用「外径 8px 的描边圆」也不要加 padding。这样 TL0 与 TL1–TL8 的占位一致，作者名不会因为档位变化而重新折行——直接满足第 7 节「徽章出现消失不得引起换行与行高变化」。

空心环与 `TL0` 文字的对比度沿用第 6.1 节 slate 行（浅色最差 7.15、深色最差 6.43），仍然不通过 opacity 降权。

### 9.4 三项后缀同时出现时的优先级

昵称 + 楼主标 + TL + 奖励 chip 是最坏情况。390px 下若超宽：**先截断昵称**，其次让奖励 chip 收缩，TL 与楼主标不缩、不换行。TL 全程 `flex: 0 0 auto`（第 2 节）。
