## 修复

### PostgreSQL 17.12：`REASSIGN OWNED` 权限检查（CVE-2026-120146）

`postgres:17-alpine` 于 2026-11-12 随 17.12 发布滚动更新。17.12 收紧了 `REASSIGN OWNED` 的调用者权限检查（[release notes](https://www.postgresql.org/docs/release/17.12/)：*Align `REASSIGN OWNED`'s caller-privilege checks with `ALTER ... OWNER TO`'s checks*，CVE-2026-120146）：PG 16 起把对象交给另一个 role 就要求能 `SET ROLE` 到该 role，但 `INHERIT TRUE, SET FALSE` 的成员关系此前可经 `REASSIGN OWNED` 绕过接收者一侧的检查；17.12 把这个缺口堵上，**接收者也必须可 `SET ROLE`**。

- **后果** —— 非超级用户宿主在 17.12 上，扩展数据库的**租约回收**、**迁移角色退役**、**扩展卸载**三条路径全部报 `must be able to SET ROLE ... (SQLSTATE 42501)`。同一份代码在 17.11 上是好的；这也是 CI `Go gate` 连续多日红的根因（CI 镜像已滚动到 17.12，本地 dev 容器仍是 17.11，于是本地恒绿、CI 恒红）。`f1567e244`
- **修法** —— 在回收事务内临时 acquire 接收者的 `SET ROLE` 权限，用完立即 release，**不留常驻成员关系**：`acquire` 走 `GRANT <owner> TO <session_user> WITH ADMIN FALSE, INHERIT TRUE, SET TRUE`，`release` 走 `REVOKE ... GRANTED BY CURRENT_USER`；旧 role 一侧继续用 `SET FALSE`（存活租约 role 是带密码的 LOGIN role，给它 `SET TRUE` 等于允许冒充，属提权）。不做常驻授权是因为扩展 owner 的成员关系本身被隔离校验要求为「无任何成员」，常驻会让下一次 provisioning 直接报 `ErrExtensionDatabaseResourceConflict`。`f1567e244`
- **grantor 维度隔离** —— `pg_auth_members` 主键是 `(roleid, member, grantor)`：`CREATEROLE` 会话建 role 时 PostgreSQL 自动留下 `grantor=<creator>, admin=true` 一行，我们的 `GRANT` 不覆盖它而是**新增**一行，`REVOKE ... GRANTED BY CURRENT_USER` 只删自己那条，creator 的 `ADMIN` 仍在（随后的 `DROP ROLE <旧 role>` 依旧成立）。PG 17.12 上逐步打印 `pg_auth_members` 实测：`CREATE ROLE` 后只有 creator 行 → `acquire` 后多出 `admin=f, inherit=t, set=t` → `release` 后只剩 creator 行，`SET ROLE owner` 报 `permission denied`、`DROP ROLE owner` 仍成功。
- **覆盖四处窗口** —— ① 建 schema（`CREATE SCHEMA ... AUTHORIZATION <owner>`，PG 16 起就要求接收者 `SET ROLE`，**与 17.12 无关**，非超级用户宿主在 17.11 上同样失败，此前被测试里手工补的 `GRANT ... SET TRUE` 盖住）；② `configure`（`REVOKE ALL ON SCHEMA` / `GRANT USAGE, CREATE` / 4 条 `ALTER DEFAULT PRIVILEGES FOR ROLE <owner>`，窗口开在函数内部，避免将来多一个调用方就漏）；③ 运行时租约默认权限（`ALTER DEFAULT PRIVILEGES FOR ROLE <lease>`，此前该缺口意味着非超级用户宿主仍发不出运行时租约）；④ 卸载（窗口卡在 `DROP SCHEMA ... CASCADE` / `DROP OWNED BY <owner>` 之前、`DROP ROLE <owner>` 之前，否则 `REVOKE` 会打在已删除的角色上）。`3d5dda827`、`193712498`
- **回归覆盖** —— 原失败用例保留「回收前宿主不得继承扩展 owner」的严格前提，改为调用生产同款 helper，并把「不得残留权限」的断言从只查 `pg_has_role(..., 'USAGE')` 扩到同时检查 `USAGE` 与 `SET`；新增非超级用户 provisioning 端到端用例，走真正的生产入口 `ensureExtensionDatabaseResources`（自然覆盖 `configure`），宿主全程不补任何接收者 GRANT。反证：注释掉 `configure` 的 acquire 报 `permission denied for schema ...`，注释掉租约默认权限的 acquire 报 `permission denied to change default privileges`。`87965eac9`、`193712498`
- 决策记录：`knowledge/decisions/2026-11-14-postgres-1712-reassign-owned-set-role.md`（含本地 17.11 / 17.12 双镜像复现表与 `pg_auth_members` 实测）。

## 升级注意

> 以下按「必须动作 / 行为变更 / 回滚风险」三类列出。**回滚风险三条（第 4–6 项）换二进制前必读。**

1. **必须执行迁移（14 个）** —— 全部标注 `+sforum OnlineSafe`，可在线应用，不需要停机窗口。`upgrade.sh` / `sforum-bootstrap.sh upgrade` 与 `sforum-migrate` 镜像会正常带出；手工部署请先跑迁移再切 API 镜像。
2. **确认 PostgreSQL 版本与数据库账号（不需要升级 PostgreSQL）** —— 本版**不要求**你动 PostgreSQL：17.11 及更早照旧工作（旧代码只在 17.12+ 上才会炸），而修复对两个版本都成立。但两种情况请务必用上本版：① 部署跑 **17.12+** 且用**非超级用户**数据库账号——旧版本的扩展租约回收 / 迁移角色退役 / 卸载会直接报 `must be able to SET ROLE ... (SQLSTATE 42501)`；② 用非超级用户账号做扩展 provisioning——建 schema 那条缺口在 PG 16 起就存在，与 17.12 无关，旧版本同样会失败。超级用户账号不受影响。`f1567e244`、`3d5dda827`、`193712498`
3. **行为变更：TL0 默认被扣下两个基线键（D34）** —— 默认安装下 **TL0 不能发新主题、不能上传附件**，TL1 起自动恢复；能回帖、能改删自己的内容。`features.trust_levels` 推荐默认 **enabled**，所以升级即生效。机制走「减法门」（零迁移、不动权限白名单与关闭语义）。若要保留旧行为，关闭 `features.trust_levels`——注意那会同时关掉整个信任等级能力，不只是这一条减法；关闭状态下 TL0 仍能开主题。`185be5701`、`knowledge/decisions/2026-11-11-trust-level-baseline-narrowing.md`
4. **回滚风险（高）：信任等级档位外观** —— 旧 API 二进制只认 9 个 token 推荐色与 16 个短名图标，读到 `#rrggbb` 或 `i-<collection>-<name>` 全名图标会 **422**（`trust.levels` 保存被拒；库内已有配置不会自动损坏，但再保存就失败）。**回滚必须同时回退该配置值，不能只回退二进制。** `f7c425c43`、`knowledge/decisions/2026-11-12-trust-level-appearance-modal-and-custom-color.md`
5. **回滚风险：信任等级条件（`rule`）** —— `trust.levels` 是**单键 JSON**，解码走 `DisallowUnknownFields`：配置里出现旧二进制不认识的字段，**整份**配置被拒绝（不是跳过那一档）。解码失败的后果是整站按未解析处理（没有任何已挣得权限、权限面等同 TL0、资料页不渲染等级卡、`identity` 侧每次求值一条 warn）。因此**从带条件的新版本回滚到不认识 `rule` 的旧版本**，顺序是：① 用**新版本**把所有档位的 `rule` 清空并保存（`PUT /admin/trust-levels`）；② 确认读回配置里 `rule` 全部消失；③ 再换回旧二进制。`e11cadca6`、`knowledge/modules/trust-levels.md` §回滚口径
6. **回滚风险：`trust.levels` 的 v1 → v2 配置形状** —— `DecodeConfig` 同时接受 `schemaVersion` 1 与 2（v1 在内存里升级），但 `EncodeConfig` **只写 v2**，旧二进制解不了 v2。回滚是**两步**：先回退镜像，**再**把 `trust.levels` 的值回退到 v1 形状；只换镜像会让站点开机读不到配置并回落到推荐默认。`color` 与 `deletedTierIds` 对更早版本同理——只有运营**真正用过**这些字段时旧二进制才整份拒绝。
7. **徽章授予通知：历史行只改键、不补发** —— `202611140001` 把历史 `badge_granted` 行改写为新键格式（等值判据，不用 `LIKE 'badge:%'`），**不补发**此前被吞掉的通知；Down 故意为空（反向退键会撞唯一约束）。升级后若有人在等旧通知，需要手工重跑一次规则回扫。`e8d6e63df`
8. **`users.top_badge_id` 语义变更** —— 从「自动推导的最高级徽章」改为「用户自由佩戴」。`202611130003` / `202611130004` 之后存量值保持原样，但用户可自行改选或选「不佩戴」（`top_badge_hidden = TRUE`）；依赖该列做「最高徽章」推导的第三方查询需要改口径。
9. **新增权限键需复核角色** —— `badge.view` / `badge.manage`（`202611100003`）与 `trust.manage`（`202611100004`）由迁移落库并映射到岗位。升级后请复核自定义角色是否具备这些键；`badge.view` 单独存在是死权限，可达性前提是 `admin.access`。
10. **`upgrade.sh` 是发布资产** —— 升级探针的静默重试改动随**本 Release 的 `upgrade.sh`** 生效。用旧 `upgrade.sh` 升级仍能工作，但看不到新的超时现场 dump 与该槽容器状态；要拿到新行为请用 `v3.1.0` 的发布资产（`sforum-bootstrap.sh upgrade --version v3.1.0` 会自动取对应版本）。`275cc66d2`
11. **产品口径说明（不是回滚）** —— 论坛读面（列表 / 详情 / 回复）的信任等级徽章与 `authorTrustLevel` 载荷已撤回（`46c2f52cb`）；等级标识只在**个人中心**呈现：资料页头部 `TL{n}` 小牌、右栏等级卡、以及两者共用的等级详情弹窗。此功能未在任何已发布版本中出现过，升级不会造成可见回退。
