`75ee2789b`

- **唯一实现 + 三份内联** —— 新增 `deploy/scripts/term-ui.sh`（`ui_init_color` 加 `ui_banner` / `ui_step` / `ui_ok` / `ui_warn` / `ui_err` / `ui_key` / `ui_prompt`），是整条一键链路唯一的配色实现。`sforum-install.sh` / `sforum-bootstrap.sh` / `sforum-latest.sh` **内联**同一份 `# >>> term-ui` … `# <<< term-ui` 块，因为它们运行在 `deploy/scripts/` 还不存在的空目录里（安装目录尚未铺开）；`deploy.sh` / `upgrade.sh` 改为 `source "$ROOT_DIR/deploy/scripts/term-ui.sh"`，配置向导、健康探针、恢复脚本改为 `source "$SCRIPT_DIR/term-ui.sh"`。四处副本的奇偶由门逐字节比对，改一处不改其余当场红。
- **六类语义标记** —— `== … ==` 标题 / 长动作开始、`==> …` 阶段推进、`[ok] …` 成功终局、`[!] …` 可继续的警告（配置键后补、跳过项、陈旧锁回收）、`[x] …` 失败、无标记的强调行承载键值与下一步命令。`upgrade.sh` 的 `say()` 拆成纯文本出口 `_say_text()` 加 `step` / `key` / `ok` / `warn` / `err` 五个组合函数；`lock_text()`（`upgrade.sh`）、`t()`（`deploy.sh`）、`msg()`（`sforum-install.sh`）保持纯文本。
- **三条不变量** —— ①**整行包裹，不拆色**：拆色（标签一色、值一色）会让 `Install directory: <path>` 这类既有 PTY 断言与操作员复制粘贴同时失效，整行包裹保证消息正文一个字节不改；②**机器前缀留在行首字节**：颜色从冒号之后开始，`tests/validate-sforum-latest.sh` 依赖的 `^sforum-latest: ` 不受影响；③**颜色只在打印点**：`t()` / `say()` / `lock_text()` 的返回值被 `$(...)` 捕获或被 `sed` / `awk` 读回，一个 ESC 字节就会让状态文件不可解析——因此 `.deployrc`、`.env.production`、`DEPLOY_LOCK_LOG`、备份脚本 stdout 一律无 ESC，配置向导的 `prompt_default` 把提示打到 stderr 正是这条不变量的直接后果。

## 修复

### 一键脚本缺备份口令时自动生成并持久化

`daf0a043d`

- **症状** —— 首次 `update` / `upgrade` 会先做一次加密备份，而 `deploy.sh` 与 `upgrade.sh` 只在口令已配好时才能继续：`v3.1.1` 的升级实测停在「在线切换前创建 PostgreSQL 备份」，提示「缺少加密密钥」，运维必须手工建口令并 `export` 才能重跑。`v3.1.1` 的 `upgrade.sh` 的 `backup_database()` 直接调 `deploy/scripts/backup-postgres.sh`，零 key 解析，而 `backup-postgres.sh` 只读进程环境。
- **修法** —— `upgrade.sh` / `deploy.sh` 新增 `resolve_backup_key` / `persist_backup_key_file` / `ensure_backup_key`，来源顺序 **shell 环境 > `.env.production` > 自动生成**：缺口令时在 `<安装目录>/.sforum/backup.key` 生成 32 字节口令（文件 0600、目录 0700，临时文件加原子 `mv` 写回 `.env.production` 的 `SFORUM_BACKUP_KEY_FILE`）；内联 `SFORUM_BACKUP_KEY` 存在时一个字节都不落盘；已有口令文件只收紧到 0600、内容不改；重复执行字节不变。`backup_database()` / `run_database_backup()` 先自举再调备份脚本，相对路径按安装目录解析成绝对路径（否则 `dirname` 得到 `.`，`chmod 700` 会打到安装目录）。
- **恢复侧只解析不生成** —— `restore_backup()` 补 `resolve_backup_key`：恢复时凭空造新口令只会把「缺密钥」变成「口令不对」；同时修掉「口令写在 `.env.production`、恢复却认不到」的既有缺口。
- **独立备份脚本未被放宽** —— `backup-postgres.sh` 一字未改，单独调用仍 fail-closed（`postgres-safety_test` 的 C3 守着）。新增 `deploy/scripts/backup-key_test.sh`（12 例：A1–A8 生成 / 幂等 / 内联不落盘 / 相对路径 / 未触发不生成 / 升级接线，B1–B4 恢复只解析、备份生成、重复执行不换口令、认得到 `.env.production` 的口令路径），挂进 `scripts/ci/release-tooling-gate.sh`。

### 显式配色开关优先于 `NO_COLOR` 与 `TERM=dumb`

`d5e8abc2f`

- **症状** —— 首轮实现把 `NO_COLOR` 放在第一分支，于是 `SFORUM_COLOR=always` 被环境变量顶掉，「用户显式要求上色」与「用户显式要求不上色」这两种显式意图得不到同一个待遇。
- **修法** —— 优先级改回 **`SFORUM_COLOR=always|never` > `NO_COLOR` > `TERM=dumb` > TTY 自动判定**：`ui_init_color` 把 `always` 放第一分支，`NO_COLOR` / `TERM=dumb` 退到第二分支；`SFORUM_COLOR=never` 无条件不上色。四处副本（`deploy/scripts/term-ui.sh` 与三份内联块）逐字节同改，块 sha256 仍一致。
- **验证** —— `tests/validate-term-ui.sh` 的开关矩阵钉住整条链：`always + NO_COLOR=1` 必须含 ESC、单独 `NO_COLOR=1` 不含、`never` 不含、`TERM=dumb` 不含、`TERM=dumb + always` 含。两份部署文档的优先级段落与热交接的 Open Question 同步为已决。

### `sforum-latest` 的机器前缀不再被 `ui_warn` 顶掉

`0b194c9e0`

- **症状** —— `ui_warn` 的格式是「标记 + 空格 + 正文」，把 `sforum-latest: ` 塞进正文会把 `[!] ` 顶到最前：无色输出变成 `[!] sforum-latest: …`，`^sforum-latest: ` 在重定向场景下同样匹配不上——**与是否上色无关**，靠 `^` 判错的外部脚本会静默失配。
- **修法** —— 改回 `die()` 的既有写法：前缀留在 byte 0、ESC 从冒号后开始、`[!]` 语义保留、仍走 stderr、正文一字不改。`tests/validate-term-ui.sh` 加静态断言：任何入口都不许用 `ui_*` 包裹 `sforum-install` / `sforum-bootstrap` / `sforum-latest` 机器前缀（变异回缺陷写法时该断言当场红）。文档措辞同步：zh 侧 `[!]` 语义行改为「配置键后补、跳过项、陈旧锁回收」；`term-ui.sh` 注释去掉「no-color.org 惯例」这一不准确依据，改成「显式开关优先于环境默认关」。

## 升级注意

1. **不需要动作** —— 无迁移、无破坏性变更、无 API 形状变更。配色层与备份口令自举都随发布资产分发（`sforum-deploy.tar.gz`、`sforum-bootstrap.sh`、`sforum-install.sh`、`sforum-latest.sh`、`upgrade.sh`），用 `upgrade.sh` 或 bootstrap 更新即生效。`deploy/scripts/term-ui.sh` 已登记进资产闭包，`sforum-bootstrap.sh` 的 `managed_files()` 会把它当作受管文件铺开。
2. **行为变更：首次 update / upgrade 不再因缺备份口令中断** —— 缺口令时自动生成 32 字节口令到 `<安装目录>/.sforum/backup.key`（0600，目录 0700），并把 `SFORUM_BACKUP_KEY_FILE` 原子写回 `.env.production`；内联 `SFORUM_BACKUP_KEY` 时零落盘；已有口令文件只收紧权限、不改内容。**口令丢失即归档不可恢复**——备份口令要跟归档一起纳入运维保管。`daf0a043d`
3. **行为变更：恢复只解析不生成** —— `restore_backup()` 现在认 `.env.production` 里的口令路径，不再「口令写在配置里、恢复却报缺密钥」；反过来它也不会替你生成新口令（那只会把「缺密钥」变成「口令不对」）。`daf0a043d`
4. **行为变更：配色优先级链** —— `SFORUM_COLOR=always|never` > `NO_COLOR` > `TERM=dumb` > TTY 自动判定。**CI 日志与重定向输出默认纯文本**；要人工在管道里看清颜色就显式 `SFORUM_COLOR=always`。显式开关压过环境默认关：`always` 压过 `NO_COLOR=1` 与 `TERM=dumb`，`never` 在任何情况下都不上色。`d5e8abc2f`
5. **不需要动作，但要知道：机器前缀仍在行首字节** —— `sforum-install: ` / `sforum-bootstrap: ` / `sforum-latest: ` 由 `^` 匹配的外部脚本不受影响；`0b194c9e0` 修的正是「`[!] ` 被顶到最前、无色输出也匹配不上」这条。`0b194c9e0`
6. **回滚风险：回退到 `v3.1.1` 的 `upgrade.sh` 需手工给口令** —— 旧 `upgrade.sh` 的 `backup_database()` 不解析 `.env.production` 的 `SFORUM_BACKUP_KEY_FILE`（`git show v3.1.1:upgrade.sh` 里零 key 解析），回退后首次升级必须 `export SFORUM_BACKUP_KEY="$(cat .sforum/backup.key)"` 才能过备份步骤；旧 `deploy.sh` 会读 `.env.production` 的 `SFORUM_BACKUP_KEY_FILE`，不受影响。新口令文件本身是纯文本十六进制，新旧脚本都能用。`daf0a043d`
7. **回滚风险：配色层是纯表现层，回退无状态残留** —— 颜色只在打印点，`.deployrc` / `.env.production` / 锁日志里没有任何 ESC 字节（门 f 断言守着），回退旧脚本不会读到被污染的状态文件。`75ee2789b`
