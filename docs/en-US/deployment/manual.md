# Manual Compose deployment

[← Deployment](../deployment.md)

This page is for operators who do not want to use `sforum-bootstrap.sh` /
`deploy.sh`: you download the deploy bundle yourself, write `.env.production`
yourself, and run migrations and startup yourself. The flow can complete a
production deployment, but it is the **fallback path**: no automatic backup,
image identity verification, deployment lock, `.deployrc`, or blue/green
switch. Production still recommends
[one-click install and update](./one-click.md).

## Differences from the script path

| Capability | Script path | Manual path |
| --- | --- | --- |
| Toolkit refresh | bootstrap does it automatically | download the new bundle and replace it yourself |
| Version resolution | stable/prerelease + immutable tag | write `SFORUM_VERSION` yourself |
| Pre-deploy backup | automatic in `deploy.sh` | run a backup yourself first |
| Image identity verification | automatic in `deploy.sh` | run `--version` yourself |
| Concurrency protection | `.deploy.lock` | none; relies on operator discipline |
| State record | `.deployrc` | none; can be generated by taking over later |
| Zero-downtime switch | `upgrade.sh` blue/green | you have to design it yourself |

## Step 0: Fetch and verify the deploy bundle

```sh
(
  set -eu
  mkdir -p sforum
  cd sforum
  curl -fsSLo sforum-deploy.tar.gz \
    https://github.com/keeptrue/SForum/releases/latest/download/sforum-deploy.tar.gz
  curl -fsSLo SHA256SUMS \
    https://github.com/keeptrue/SForum/releases/latest/download/SHA256SUMS
  awk '$2 == "sforum-deploy.tar.gz" { print }' SHA256SUMS > sforum-deploy.sha256
  test "$(wc -l < sforum-deploy.sha256 | tr -d '[:space:]')" = 1
  if command -v sha256sum >/dev/null 2>&1; then
    sha256sum -c sforum-deploy.sha256
  else
    shasum -a 256 -c sforum-deploy.sha256
  fi
  if command -v gh >/dev/null 2>&1; then
    gh attestation verify sforum-deploy.tar.gz --repo keeptrue/SForum
  fi
  tar -xzf sforum-deploy.tar.gz --strip-components=1
)
```

When pinning a version, replace both `latest/download` URLs with
`download/<TAG>/...`. If verification fails, do not extract, and above all do
not run scripts from the bundle.

## Step 1: Host preparation

- Linux `amd64` or `arm64`; Windows is not supported.
- Docker Engine and Docker Compose `2.24.4+`.
- `curl`, `tar`, `openssl` (or `/dev/urandom`).
- A domain pointing at this host; host Caddy/Nginx handles TLS.
- Loopback `WEB_PORT` and `API_PORT` are available.

## Step 2: Write `.env.production`

Copy the example, then change the values:

```sh
cp .env.production.example .env.production
chmod 600 .env.production
```

The minimum required entries are below. For the full reference see
[environment variables and secrets](./environment.md).

| Variable | Requirement |
| --- | --- |
| `APP_ENV` | must be `production` |
| `APP_URL` | the public `https://` address |
| `SFORUM_VERSION` | a concrete immutable tag, for example `<TAG>` |
| `POSTGRES_PASSWORD` | at least 32 characters; `openssl rand -hex 32` is recommended |
| `DATABASE_URL` | `postgres://sforum:<same-password>@postgres:5432/sforum?sslmode=disable` |
| `REDIS_PASSWORD` | at least 32 characters |
| `SESSION_HASH_SECRET` | at least 32 characters |
| `IDENTITY_SUBJECT_HMAC_SECRET` | at least 32 characters |
| `APP_OPTION_ENC_KEY` | 64-character hex |
| `ALTCHA_SECRET` | at least 32 characters |
| `MARKETPLACE_ED25519_PUBLIC_KEY_HEX` | 64-character hex; the official Marketplace needs the official public key |
| `CSRF_TRUSTED_ORIGINS` | the public site origin, for example `https://forum.example.com` |
| `NUXT_PUBLIC_API_BASE_URL` | must be `/api/v1` |
| `NUXT_PUBLIC_ADMIN_ROUTE_PREFIX` | a safe path, for example `/control-panel` |
| `MIGRATE_ON_STARTUP` | `false` is recommended, then run migrations explicitly |

Generate secrets:

```sh
openssl rand -hex 32   # repeat for each secret, one value per secret
```

`APP_DOMAIN` is only used by the host Caddy example and never enters the
application container. The wizard writes client-IP settings that fit the
standard Compose topology: `TRUST_PROXY` on, private-network peers trusted,
loopback not trusted, `TRUSTED_PROXIES` empty. When a CDN sits in front, put its
egress ranges into Caddy's `servers.trusted_proxies` (see
`deploy/caddy/Caddyfile`) and leave the app-side `TRUSTED_PROXIES` empty; set
`TRUST_PROXY=false` to stop honouring forwarded headers entirely.

## Step 3: Validate the Compose expansion

Define a shell array first and reuse it in every later command:

```sh
COMPOSE=(docker compose --env-file .env.production \
  -f compose.yaml -f compose.prod.yaml -f compose.release.yaml)

# The later docker run commands need the same tag, so read it from the env file and export it.
SFORUM_VERSION="$(sed -n 's/^SFORUM_VERSION=//p' .env.production)"
export SFORUM_VERSION

"${COMPOSE[@]}" --profile tools config --quiet
```

`--profile tools` makes the `migrate` service participate in the expansion
check. `config --quiet` checks variable interpolation, service definitions, and
whether `SFORUM_VERSION` exists. `compose.release.yaml` fails outright on a
missing version; that fail-closed behavior is intentional.

## Step 4: Pull and verify the images

```sh
"${COMPOSE[@]}" pull migrate api web

docker run --rm "ghcr.io/keeptrue/sforum-api:${SFORUM_VERSION}" sforum-api --version
docker run --rm "ghcr.io/keeptrue/sforum-migrate:${SFORUM_VERSION}" sforum-migrate --version
```

The output should contain `SForum <version>`. If the tag is wrong or the
registry returned a different build, do not continue starting.

## Step 5: Start dependencies, migrate, start the application

```sh
"${COMPOSE[@]}" up -d --wait postgres redis
"${COMPOSE[@]}" run --rm -T --pull never migrate
"${COMPOSE[@]}" up -d --no-build --pull never postgres redis api web
```

The order cannot be reversed: migrations must finish before the API starts.
`--pull never` ensures migration and startup use the local images that were
just verified, so no registry dependency appears after the old application
stops.

If you set `MIGRATE_ON_STARTUP` to `true`, the API also attempts migration at
startup; either mode is fine, but do not set it to `false` and then skip
running `migrate`.

## Step 6: Health checks

```sh
curl -fsS "http://127.0.0.1:${API_PORT:-18080}/api/v1/ready"
curl -fsS "http://127.0.0.1:${WEB_PORT:-3000}/health"

"${COMPOSE[@]}" ps
"${COMPOSE[@]}" logs --tail=200 api web
```

`/api/v1/ready` depends on PostgreSQL; when Redis or Meili is unavailable it
reports degraded readiness instead of taking the whole site down.

## Step 7: Reverse proxy and TLS

The host Caddy example is in `deploy/caddy/Caddyfile`. The core goals:

- Ordinary HTTP points at `127.0.0.1:${WEB_PORT:-3000}`; same-origin
  `/api/v1/*` is forwarded by Nuxt to `api:8080`.
- WebSocket Upgrade points at `127.0.0.1:${API_PORT:-18080}`.
- TLS terminates on the host; containers do not listen publicly.
- Client IP handling is already on: the API peer is the `web` container, so
  trusting private-network peers is enough and a host Caddy needs no
  `TRUSTED_PROXIES` entry (the API never sees Caddy's address). With a CDN in
  front, put its egress ranges into Caddy's `servers.trusted_proxies`; Caddy
  deletes `CF-Connecting-IP` / `True-Client-IP` and recomputes the real client.
  Do not write `0.0.0.0/0`.

The Caddy process reads host environment variables, not the
`.env.production` inside the containers:

```sh
APP_DOMAIN=forum.example.com WEB_PORT=3000 API_PORT=18080 caddy run \
  --config deploy/caddy/Caddyfile --adapter caddyfile
```

## Step 8: First administrator and site settings

Open `APP_URL` in a browser and register the first account; that account
becomes a protected `super_admin`. The admin panel address is
`APP_URL + NUXT_PUBLIC_ADMIN_ROUTE_PREFIX`, `/control-panel` by default.

Then configure the site name, HTTPS URL, SMTP, attachment storage, and search
in the admin panel. Without mail configuration, password reset and
notifications are unavailable.

## Step 9: First backup

```sh
./deploy.sh --action backup
```

It starts `postgres` first, then writes the backup to
`backups/<db>-<UTC>.sql` with mode `0600`. `SFORUM_BACKUP_DIR` can point at a
host path instead. Do not leave backup files only inside a container volume.

## Manual update

```sh
# 1. Back up first
./deploy.sh --action backup

# 2. Set SFORUM_VERSION in .env.production to the target tag and re-export it
SFORUM_VERSION="$(sed -n 's/^SFORUM_VERSION=//p' .env.production)"
export SFORUM_VERSION

# 3. Pull and verify
"${COMPOSE[@]}" pull migrate api web

# 4. Stop the app, migrate, then start
"${COMPOSE[@]}" stop api web
"${COMPOSE[@]}" run --rm -T --pull never migrate
"${COMPOSE[@]}" up -d --no-build --pull never postgres redis api web

# 5. Health checks
curl -fsS "http://127.0.0.1:${API_PORT:-18080}/api/v1/ready"
curl -fsS "http://127.0.0.1:${WEB_PORT:-3000}/health"
```

This is a stop-the-world update: the site is unavailable while `api`/`web`
are stopped. When you need zero downtime, use `upgrade.sh` instead of
imitating blue/green by hand.

## Manual rollback

Roll back only the images, and only after confirming the database migrations
are backward compatible:

```sh
# Set SFORUM_VERSION back to the old tag and re-export it
SFORUM_VERSION="$(sed -n 's/^SFORUM_VERSION=//p' .env.production)"
export SFORUM_VERSION
"${COMPOSE[@]}" pull migrate api web
"${COMPOSE[@]}" stop api web
"${COMPOSE[@]}" up -d --no-build --pull never postgres redis api web
```

When the migration is not compatible, rolling back the images makes the old
code read the new table structure. Restore the pre-deployment backup instead:

```sh
SFORUM_CONFIRM_RESTORE=RESTORE ./deploy.sh --action restore
```

The restore script imports into a separate temporary database in a single
transaction and atomically swaps database names only after validating the
application tables; any SQL error leaves the original database in place.

## Handing back to script management

A manual installation has no `.deployrc`, so a bootstrap upgrade refuses to
run. Run one deploy action first so `deploy.sh` records the state:

```sh
./deploy.sh --action deploy --version <TAG>
```

It backs up, migrates, starts, and writes `.deployrc`. After that you can use
`./sforum-bootstrap.sh upgrade` and blue/green updates.
